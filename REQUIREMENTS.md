# Аудит проекта и требования к исправлению

Дата проверки: 24 октября 2026 года.

## Вердикт

Проект запускается, но требованиям `HW.md` не соответствует. Текущие тесты проверяют только 7 happy-path сценариев и пропускают основные инварианты задания: восстановление, бюджеты, задачи, защиту от конфликтов и безопасность Bash. До защиты это состояние принимать нельзя.

Сейчас проходят `python3 -m unittest discover -v` (7 тестов) и `python3 -m ruff check agent tests`. Это не доказывает выполнение уровней 8–10: обязательные сценарии из `HW.md` в тестах отсутствуют.

## P0 — немедленно исправить

### 1. Секрет закоммичен в рабочем дереве

Файл `.env` отслеживается Git (`git ls-files .env`) и содержит `OPENAI_API_KEY` с префиксом `sk-`. `.gitignore` защищает только будущие добавления.

Требование: немедленно отозвать ключ, удалить секрет из индекса и истории, оставить placeholder в `.env.example`, проверить `git grep` и добавить автоматическую проверку на секреты. Ключ нельзя включать в отчёты, логи и diff.

### 2. Bash позволяет обходить policy

`agent/tools.py:142–167` использует `shell=True`, проверяет только несколько символов и почти не проверяет аргументы. Перевод строки не запрещён; `git status`/`git diff` принимают произвольные опции, включая варианты записи вывода; `pytest` может загрузить плагины и выполнить побочный код. stdout/stderr ограничиваются только после завершения процесса, поэтому память не ограничена.

Требование: запускать argv с `shell=False`, запретить управляющие символы и опции записи, разрешать точный набор подкоманд и аргументов, ограничивать потоковый вывод и гарантированно завершать процесс по таймауту. Расширение allowlist журналировать и тестировать.

### 3. Нет проверки дерева перед изменяющим действием

`_record_changes()` (`agent/tools.py:176–211`) создаёт снимок только после записи. Последний снимок не сравнивается с текущим деревом перед `write_file` или потенциально изменяющим Bash. После первого `write_file` внешняя правка, а затем второй `write_file`, перезаписывает внешний текст без конфликта.

Требование: сохранять baseline до первого действия и перед каждым изменением сравнивать полный набор путей и содержимое; при расхождении останавливать действие до записи. Учитывать создание, удаление, бинарные файлы и символические ссылки.

### 4. Бюджет пачки расходуется неатомарно

`agent/runtime.py:132–165` резервирует только число tool calls. Effect-бюджет проверяется внутри цикла. При двух `write_file` и `effects=1` первый файл меняется, затем runtime падает на втором. По `HW.md` при нехватке остатка не должен выполняться ни один вызов пачки.

Требование: заранее посчитать лимиты пачки (tools, effects и известные части результата), атомарно зарезервировать их и только потом запускать инструменты. При неизвестном размере выдавать строго помещающийся обрезанный результат с `truncated=true`.

## P1 — блокирует соответствие заданию

### 5. Схемы инструментов не валидируются

JSON Schema (`agent/tools.py:58–107`) не используется для проверки типов, обязательных и лишних полей. `read_file` без `path` вызывает необработанный `KeyError` (`agent/tools.py:126`), а не результат для модели. Неверные типы ведут к аналогичным сбоям.

Требование: единый валидатор имени и JSON-объекта до запуска; ошибки схемы должны стать сообщением `role=tool`. Добавить тесты на неизвестный инструмент, пропущенное поле, неверный тип и лишнее поле.

### 6. Нарушена идемпотентность и protocol error

При уже успешном `tool_call_id` runtime (`agent/runtime.py:135–139`) возвращает старый результат без сравнения имени и аргументов. Повтор того же ID с другим инструментом или содержимым ошибочно считается успешным, хотя `HW.md` требует protocol error.

Требование: канонизировать имя и аргументы, сравнивать с первой попыткой и отклонять любое расхождение. Повтор успешного вызова должен быть идемпотентным.

### 7. Recovery/retry не повторяет инструмент

`resolve(..., retry)` (`agent/runtime.py:206–214`) записывает `retrying`, но не исполняет сохранённый вызов заново: он просто вызывает модель. Retry должен создать новую попытку того же tool call с теми же аргументами и пройти проверки бюджета и конфликта.

### 8. Сбой между действием и журналом не моделируется

Reserve, запись `started`, выполнение и запись результата находятся в разных автокоммитах (`agent/runtime.py:141–165`, `agent/storage.py:27`). Нет управляемой fault point между выполнением и результатом; `resume()` безусловно помечает все `started` как `unknown`, включая не начавшиеся вызовы. Решение пользователя о принадлежности обнаруженных изменений запуску не сохраняется.

Требование: транзакционно фиксировать reserve + `started`, добавить fault injection, на resume показывать дерево/изменения и требовать явное решение.

### 9. Plan Mode формально есть, задачи не работают

`approve()` создаёт строки задач (`agent/runtime.py:52–69`), но runtime не назначает `task_id` tool call, не проверяет зависимости, не переводит задачи в `done`, не сохраняет evidence и не пропускает завершённые задачи после resume. `Store.task_status()` нигде не вызывается.

Требование: валидировать план, строить граф задач, запускать только задачу с выполненными зависимостями, привязывать каждый call к задаче и завершать её по машинно проверяемому результату. Нужен тест минимум на три задачи с зависимостью и повторный resume.

### 10. Неверные переходы approval/rejection

`reject()` оставляет `phase='planning'` (`agent/runtime.py:44–50`), а `approve()` проверяет только phase (`runtime.py:52–56`). Отклонённый план можно снова утвердить. Нужна state machine `waiting_approval -> approved/rejected` с терминальными состояниями.

### 11. Resume запускает завершённый run заново

`resume()` не проверяет `status` и всегда входит в loop. Завершённые сообщения снова отправляются модели, возможны новые действия и расходы. Завершённые действия и задачи после resume запускаться не должны.

### 12. Rollback неполон

`rollback()` (`agent/runtime.py:216–230`) работает только с текстом и не создаёт родительские каталоги перед восстановлением. Откат вложенного файла после удаления каталога может завершиться `FileNotFoundError`. `_tree()` пропускает бинарные файлы и не описывает симлинки.

Требование: атомарный rollback всех отслеживаемых объектов, создание каталогов, проверка всех хешей до первой записи и отсутствие частичного отката при конфликте.

## P2 — качество и совместимость

### 13. Ограничения чтения и результата не соблюдаются

`read_file()` читает файл целиком без лимита. Bash сначала собирает полный вывод в память и только потом берёт последние 20 000 символов. Обрезанный JSON может быть больше остатка result budget (`runtime.py:157–163`), после чего reserve падает уже после побочного действия.

Требование: потоковое ограничение размера, точный учёт байтов и валидный результат в пределах остатка.

### 14. Ошибки инструментов не всегда продолжают цикл

Перехватываются только `ToolError`, `OSError`, `ValueError`. `KeyError`, `TypeError`, `UnicodeDecodeError` и `subprocess.TimeoutExpired` могут уронить run вместо `role=tool` и продолжения модели.

Требование: валидировать вход заранее, использовать доменные ошибки и возвращать контролируемый timeout-результат.

### 15. CLI и документация расходятся

README использует `resolve <run_id> <call_id> retry`, старый документ описывал `--retry`, а CLI принимает только позиционный action (`agent/__main__.py:23–27`). Нет команды просмотра бюджета, решений и unknown-вызовов. `main()` не обрабатывает `sqlite3.IntegrityError` и `KeyError` при повторном или неполном запуске.

Требование: выбрать один контракт CLI, документировать его и покрыть smoke-тестами всех команд.

### 16. Контрольный проект и тесты недостаточны

`workspace/test_order.py` сжат и не является копией формата из `HW.md`. Тесты агента не проверяют Bash для проверки исправления, неизменность теста, recovery fault point, счётчики после resume, каждый бюджет, зависимости задач, diff и внешний конфликт.

Требование: добавить детерминированные fake model/clock/fault injector тесты по всем 12 обязательным сценариям `AGENTS.md`, не меняя контрольный тест ради прохождения.

## Минимальная матрица приёмки после исправлений

1. Два и более tool call в одной реплике выполняются только после атомарной проверки всей пачки.
2. Неизвестное имя, плохая схема, ошибка инструмента и timeout возвращаются модели как `role=tool`.
3. `order.py` исправляется агентом, `python3 -m unittest -v` запускается через Bash, `test_order.py` byte-for-byte неизменен.
4. Fault injection между side effect и результатом переводит вызов в `unknown`; retry/fail/abort различаются и журналируются.
5. Лимиты model/tools/effects/result исчерпываются отдельными тестами и сохраняются после resume.
6. Plan Mode разрешает только чтение до approve; reject необратим; после approve работают три зависимые задачи с evidence.
7. Перед каждым изменением обнаруживается внешняя правка; при конфликте нет частичной записи.
8. Diff показывает создание, изменение и удаление; rollback после перезапуска восстанавливает только файлы текущего run и останавливается до любой записи при конфликте.
9. Ruff и полный `python3 -m unittest discover -v` проходят; секретов в Git, логах и артефактах нет.
