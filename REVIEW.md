# Обзор проекта: соответствие HW.md и что необходимо исправить

Дата: 29 октября 2026 года. Проверенная ревизия: `0e3d808`, с учётом текущего рабочего дерева. Основа обзора: [HW.md](HW.md), [README.md](README.md), [AGENTS.md](AGENTS.md), весь код `agent/` и `tests/`.

**Вердикт.** В проекте есть почти все сущности из ТЗ, но несколько основных гарантий не работают. Самые серьёзные проблемы находятся именно там, ради чего написано задание: атомарность, восстановление, разрешение неопределённых действий и безопасный откат. Наличие таблиц `calls`, `budgets`, `snapshots` и `changes` пока создаёт более сильное впечатление надёжности, чем обеспечивает реализация.

Успешный обычный сценарий работает. Однако сейчас я не считал бы даже базовый уровень на 7 баллов полностью подтверждённым: сломаны существенные сценарии recovery, есть обход Plan Mode, а инструмент `bash` фактически не запускает Bash. Уровни 8–10 требуют исправлений, а не только демонстрации существующих команд. Это техническая оценка соответствия, не прогноз балла преподавателя.

Воспроизведения не обращались к внешним API и не изменяли исходный код проекта. В отчёте отдельно обозначены проверки выполнением и выводы из чтения кода. **Приоритеты.** `P0` — риск потери/перезаписи данных или фундаментально неверное состояние; исправлять первым. `P1` — нарушение обязательного поведения ТЗ или существенный сбой. `P2` — важная неполнота, диагностическая или архитектурная проблема. Это приоритеты исправления в этом проекте, не внешняя шкала уязвимостей.

**1. P0 — Каждый обычный вызов оставляет незавершённую попытку.**

Места: [agent/runtime.py](agent/runtime.py), строки 278–293, 314–359, 415–427; [agent/storage.py](agent/storage.py), строки 154–167, 180–198.

`reserve_batch()` вставляет попытку № 1 со статусом `started`. Затем `_execute_call()` читает именно её, вычисляет `attempt = prior.attempt + 1` и сохраняет успешный результат уже как попытку № 2. Первая запись остаётся `started` навсегда. Фактически один запуск инструмента записывается как две попытки.

**Подтверждено:** после успешного `write_file` и прерывания следующего запроса к модели в БД находятся `(1, started)` и `(2, succeeded)`. `resume()` объявляет вызов неизвестным, а `resolve(call_id, 'retry')` отвечает `call is not unknown`: он смотрит последнюю, успешную попытку. Пользователю предлагается действие, которое runtime сам же запрещает. Обычный `completed` маскирует проблему ранним выходом из `resume()`.

**Исправить:** завершать ту же попытку, которая зарезервирована перед исполнением. Новая попытка нужна только при явном повторе. Recovery должен анализировать актуальное состояние вызова, а не любую историческую строку `started`.

**Регрессия:** один успешный вызов — одна завершённая попытка; сбой после него не делает этот вызов unknown; явный retry добавляет ровно одну попытку и не повторяет уже успешное действие.

**2. P0 — Атомарных транзакций бюджетов на самом деле нет.**

Место: [agent/storage.py](agent/storage.py), строки 27, 124–167.

Соединение открывается с `isolation_level=None`, то есть в autocommit. Блок `with self.db:` сам по себе не начинает транзакцию. Поэтому проверка лимитов, несколько списаний и вставки `started` выполняются отдельными коммитами. Название теста `test_batch_effect_budget_is_atomic` вводит в заблуждение: он проверяет предварительный отказ, но не атомарность записи.

**Подтверждено:** передать `reserve_batch()` две записи с одинаковым первичным ключом. Вторая вставка падает с `IntegrityError`, но в БД остаются списания `tools=2`, `effects=2` и первая строка вызова. SQL trace не содержит `BEGIN`. Повторный ID в одной пачке не отклоняется runtime до этой операции.

При обычном аварийном завершении существует такое же окно между отдельными UPDATE/INSERT. Проверка и списание в `reserve()` также не защищены от конкурирующих соединений.

**Исправить:** явная транзакция, например `BEGIN IMMEDIATE` с commit/rollback; в ней проверять лимиты, списывать полную пачку и создавать все попытки. Отдельно заранее валидировать уникальность ID внутри ответа. Не возвращать бюджет после успешно зафиксированного резервирования и последующего сбоя инструмента: это уже другое окно и прямое требование ТЗ.

**Регрессия:** исключение после каждого SQL-шага до commit оставляет состояние целиком прежним; после commit — целиком зарезервированным; два соединения не могут превысить общий лимит.

**3. P0 — После сбоя между изменением файла и журналом нет рабочего протокола восстановления.**

Места: [agent/tools.py](agent/tools.py), строки 214–231, 254–255, 314–346; [agent/runtime.py](agent/runtime.py), строки 402–489; [agent/__main__.py](agent/__main__.py), строки 126–141.

Файл изменяется до `_record_changes()`. Это неизбежное окно между файловой системой и БД, которое ТЗ специально требует разрешать через пользователя. Но `resume()` показывает лишь ID вызова. Он не сравнивает дерево со снимком, не показывает найденный diff и не спрашивает, считать ли изменения принадлежащими запуску. `rollback()` вообще не проверяет наличие `started`/`unknown`.

**Подтверждено:** прерывание в `_record_changes()` после записи файла оставляет новый файл и пустой журнал. `resume()` объявляет unknown. `rollback()` успешно возвращается, не восстановив файл. Явный retry затем получает `workspace conflict detected before side effect`: текущее дерево отличается от старого снимка именно из-за собственного прерванного действия.

Дополнительно снимок и строки changes пишутся отдельными коммитами. Сбой после записи снимка, но до всех строк журнала создаёт ещё одну разновидность неполного состояния.

**Исправить:** сохранять привязанный к попытке снимок до действия; после сбоя вычислять различия, показывать их пользователю и сохранять его явное решение о принадлежности изменений. До разрешения всех unknown запрещать откат и новые меняющие действия. Итоговый снимок и весь журнал завершённого действия фиксировать транзакционно. Для каждого инструмента определить условия безопасного retry; произвольный запуск тестов нельзя автоматически считать повторяемым без последствий.

**Регрессия:** сбои после реального изменения, после вычисления diff, между строками журнала и перед сохранением результата. Пользователь видит изменения, решение переживает перезапуск, rollback до решения запрещён.

**4. P0 — Откат не восстанавливает исходные байты и способен испортить файл.**

Места: [agent/tools.py](agent/tools.py), строки 33–54; [agent/runtime.py](agent/runtime.py), строки 478–489.

Для бинарного файла снимок хранит только строку `<binary:HASH>`. Откат записывает эту строку как содержимое файла. Текст читается с нормализацией переводов строк, поэтому исходные CRLF тоже не сохраняются. Типы файла кодируются строковыми префиксами: обычный текст `<symlink:...>` при восстановлении будет интерпретирован как ссылка.

**Подтверждено:** исходные байты `b'\xff\x00\xfe'` после write/rollback заменены текстом `<binary:...>`; `b'a\r\nb\r\n'` восстановлены как `b'a\nb\n'`. Коллизия с `<symlink:...>` следует непосредственно из ветки восстановления, отдельно не запускалась.

Это не требование сделать профессиональную файловую систему. Даже ограниченный учебный агент должен либо точно восстановить поддерживаемый файл, либо заранее отказать в операции над неподдерживаемым типом. Текущая версия принимает файл, обещает rollback и теряет данные.

**Исправить:** отдельные поля `kind`, исходные байты/BLOB, target ссылки и хеш байтов. Diff для UTF-8 строить как представление, а не как единственный источник восстановления. Если бинарные файлы вне scope — явно запрещать их изменение/удаление до эффекта. Для полноценного восстановления учитывать хотя бы исполняемый бит.

**Регрессия:** бинарный файл, CRLF, пустой файл, текст с зарезервированным префиксом, создание/удаление, ссылки и права поддерживаемых файлов.

**5. P0 — Run можно восстановить и откатить в чужом workspace.**

Места: [agent/runtime.py](agent/runtime.py), строки 36–40, 402–405, 464–479; [agent/__main__.py](agent/__main__.py), строки 73–81, 173, 227; [agent/storage.py](agent/storage.py), строки 42–45.

Workspace сохраняется в `runs`, но при восстановлении runtime использует текущий `args.workspace`. Нет загрузки сохранённого пути и проверки совпадения. Сохранённый путь к тому же может быть относительным и поменять смысл после смены cwd.

**Подтверждено:** выполнить изменение в каталоге A, создать runtime с тем же `run_id` и каталогом B, где файл случайно совпадает с final hash. `rollback()` записывает оригинальное содержимое A в файл B; A остаётся изменённым. Проверка хешей не защищает от выбора неправильного проекта.

**Исправить:** сохранять канонический абсолютный корень и связывать с ним run. На resume брать корень из сохранённого состояния; явное несовпадение параметров отклонять. Перенос проекта, если нужен, делать отдельной проверяемой операцией.

**Регрессия:** восстановление из другого cwd и с другим `--workspace` не изменяет ни одного файла постороннего проекта.

**6. P1 — Unknown можно пропустить; fail не завершает вызов; abort не является окончательным.**

Место: [agent/runtime.py](agent/runtime.py), строки 402–462.

`resume()` ищет только `started`, переводит их в `unknown` и возвращает вопрос. При следующем `resume()` уже существующие unknown не проверяются, и runtime снова идёт к модели. `resolve(..., 'fail')` добавляет tool-сообщение, но не обновляет статус попытки. Ни fail/retry/abort не сохраняются в `decisions`. `abort` ставит общий `failed`, однако `resume()` не считает его терминальным.

**Подтверждено:** два последовательных resume завершают run ответом модели при всё ещё существующем unknown. В другом сценарии после выбора fail вызов остаётся `unknown`, run становится `completed`, в decisions нет ни одной записи.

По коду есть и проблемы пачки: разрешение первого unknown немедленно вызывает модель, хотя другие вызовы той же пачки ещё не разрешены. CLI продолжает обход после выбора abort. Любое неизвестное значение `action`, переданное прямо в API `resolve()`, попадает в ветку retry; CLI фильтрует его, core — нет.

**Исправить:** явные переходы состояний. Пока есть хотя бы один unresolved call, модель и новые эффекты не запускаются. Сохранять решение и итог попытки атомарно; fail должен действительно закрывать вызов, abort — останавливать запуск. Допустимые действия проверять в core, правила безопасного retry задавать у инструмента.

**Регрессия:** два перезапуска до ответа пользователя, fail после restart, abort плюс resume, пачка из нескольких unknown, недопустимое значение action.

**7. P1 — Сохранённый результат не гарантирует восстановление корректной истории сообщений.**

Места: [agent/runtime.py](agent/runtime.py), строки 237, 291–307, 350–359, 402–430; [agent/storage.py](agent/storage.py), строки 77–103.

Assistant tool_calls, попытка, result и сообщение `role: tool` сохраняются раздельно. При сбое после сохранения result, но до `add_message(..., 'tool', ...)`, recovery не достраивает сообщение из сохранённого результата. При сбое после assistant-сообщения, но до резервирования пачки, вызовы тоже не восстанавливаются из истории.

**Подтверждено:** прерывание на добавлении tool-сообщения. После возобновления модель получает историю с ролями `system, user, assistant`, где у assistant есть tool_calls, но ответа на них нет, хотя `calls` содержит succeeded. В проверке потребовалось повторное resume из-за отдельной ошибки № 1. Подставная модель это принимает; корректность такого диалога с реальным провайдером не подтверждена.

**Исправить:** перед новым запросом восстанавливать все недостающие tool-сообщения из результатов, не исполняя инструменты повторно. Связать завершение попытки, запись результата, сообщения и прогресса задачи одной транзакцией там, где это возможно. Учитывать и уже сохранённую, но ещё не зарезервированную пачку.

**Регрессия:** fault injection между каждой парой этих этапов; после reopen БД на каждый tool_call есть ровно один корректный ответ, повторных эффектов нет.

**8. P1 — Утверждение плана можно обойти обычным сообщением.**

Места: [agent/runtime.py](agent/runtime.py), строки 108–117, 432–462; [agent/__main__.py](agent/__main__.py), строки 253–262.

`continue_prompt()` запрещает лишь `rejected` и `failed`, затем безусловно ставит `phase='executing'` и вызывает `_safe_loop(False)`. Для `waiting_approval` это превращает обычное уточнение пользователя в разрешение на запись. Доступно, в частности, после восстановления сохранённого плана. `resolve()` тоже жёстко использует `plan_mode=False`, даже если прерванный вызов относился к планированию.

**Подтверждено:** start(plan=True), затем `continue_prompt('уточнение')`; модель вызывает write_file, содержимое меняется, решений об утверждении в БД нет.

**Исправить:** разрешённость эффекта выводить из сохранённой фазы и отдельного утверждения в БД, а не из bool, передаваемого вызывающим кодом. Новые сообщения в Plan Mode должны продолжать планирование или редактировать план. Resolve не должен менять фазу.

**Регрессия:** обычный follow-up, resume и retry до утверждения блокируют write/delete/bash и сохраняют режим планирования.

**9. P1 — Восстановление планирования теряет план, утверждение не является единой операцией.**

Места: [agent/runtime.py](agent/runtime.py), строки 127–142, 162–191, 263–266, 402–430.

Начальный запуск вызывает `_planning()`, который разбирает и сохраняет план. Resume вызывает только `_safe_loop(True)`: финальный JSON остаётся сообщением, run получает completed, а сохранённого плана нет. Есть также окно между завершением `_loop(True)` и сохранением плана: completed уже зафиксирован, и следующий resume выйдет раньше времени.

**Подтверждено:** прервать первый запрос при планировании, затем resume с корректным JSON. Результат — `status='completed'`, `plan_json=NULL`; утверждать нечего.

По коду `approve()` отдельно фиксирует решение, фазу, каждую задачу и сообщение. Сбой посередине оставит approved с неполным набором задач. Проверки/восстановления этого перехода нет. В execution также остаётся первоначальное системное сообщение planner, требующее read-only и финальный JSON; это создаёт противоречивый контекст для модели.

**Исправить:** единый механизм запуска/возобновления фазы планирования; финальный статус выставлять после сохранения валидного плана. Решение, полный набор задач и переход к execution сохранять транзакционно. Формировать контекст модели с учётом текущей фазы.

**Регрессия:** сбой на каждом этапе планирования/approve, reopen БД, ровно один полный набор задач, сохранённый план и корректный статус ожидания.

**10. P1 — Исчерпание result-бюджета обнаруживается уже после побочного эффекта.**

Места: [agent/runtime.py](agent/runtime.py), строки 291–295, 342–350, 384–400, 439–461; [agent/tools.py](agent/tools.py), строки 188–197, 284–311.

Executor не получает доступный остаток. Сначала инструмент полностью выполняется, затем `_fit_result()` пытается уместить результат. При нулевом остатке не помещается даже оболочка truncation, и runtime падает после изменения. Это прямо противоречит требованию не начинать действие при исчерпанном нужном лимите.

**Подтверждено:** `result=0`, остальные лимиты положительные, один write_file. Файл изменён, ошибка — `result budget exhausted`, попытка осталась started. Это также может произойти в середине пачки после расходования остатка первым результатом.

Ограничения инструментов тоже неполны: read_file сначала делает `read_bytes()` целиком; stdout/stderr Bash независимо режутся до 20 000 байт, но поле `truncated` не возвращается. Подтверждено на выводе 30 000 символов: получены 20 000 и никакой отметки об усечении. Ветка resolve/fail вообще добавляет результат вне `_fit_result()`.

**Исправить:** перед исполнением гарантировать место для минимального результата; передавать остаток executor и читать/собирать данные ограниченно. Все пути выдачи результатов должны учитывать единый бюджет. Сохранять валидную структуру результата с явным признаком неполноты; отдельно определить учёт повторной выдачи кэшированного результата.

**Регрессия:** ноль, остаток меньше минимального ответа, точная граница, UTF-8, два результата в пачке, retry/fail, перезапуск после списания. При невозможности выдать минимальный результат изменение не начинается.

**11. P1 — Таймаут Bash не ограничивает реальное время выполнения.**

Место: [agent/tools.py](agent/tools.py), строки 284–311.

После сигнала готовности selector вызывается `BufferedReader.read(4096)`. Готовность означает наличие каких-то байтов, а не всех 4096. Чтение может ждать остальные данные/EOF, и до очередной проверки deadline программа не дойдёт. Кроме того, `process.kill()` останавливает только непосредственный процесс: потомки могут удерживать stdout/stderr открытыми. `process.wait()` в конце также без timeout.

**Подтверждено:** процесс печатает один символ с flush и спит 0,8 секунды. При timeout 0,1 секунды `_collect()` возвращается примерно через 0,83 секунды. Указанный срок не соблюдён. Сценарий с потомком не запускался, вывод следует из управления процессами в коде.

**Исправить:** неблокирующее чтение дескрипторов с общим deadline, ограниченное завершение и ожидание всей группы процессов, гарантированное закрытие pipe и selector. Проверка должна работать и для молчащего процесса, и для частичного вывода, и после закрытия обоих потоков до завершения процесса.

**Регрессия:** частичный stdout + sleep, одновременно заполненные stdout/stderr, дочерний процесс с унаследованными потоками, раннее закрытие потоков. Время завершения ограничено заданным timeout плюс небольшой допуск на уборку.

**12. P1 — Проверка путей не распространяется на аргументы Bash.**

Места: [agent/tools.py](agent/tools.py), строки 25–30, 233–282.

Для файловых инструментов разрешается абсолютный путь, если он находится внутри workspace, хотя AGENTS.md требует относительные пути. Для Bash проверяются отдельные строковые шаблоны, но не фактические разрешённые пути. Символьные ссылки и значения внутри `--option=value` эту проверку обходят. Для `python3 -m pytest` любые последующие опции разрешены.

**Подтверждено:** ссылка `workspace/alias` на соседний временный каталог; `bash(command='ls alias/')` выводит имя файла вне workspace. Проверка argv также принимает `python3 -m pytest --junitxml=../outside/result.xml` и `python3 -m pytest --override-ini=cache_dir=../outside/cache`. Для этих двух команд проверена именно валидация, а не запуск pytest. Абсолютный путь внутри workspace успешно прочитан файловым инструментом.

Есть и более общая граница: тесты выполняют Python-код с правами процесса, поэтому список имён команд сам по себе не запрещает изменение исходников. ТЗ допускает доверенный учебный workspace без секретов — полноценная системная песочница здесь не обязательна. Но README не должен выдавать allowlist за гарантию отсутствия произвольных эффектов от исполняемых тестов.

**Исправить:** ограничить конкретные формы argv, отдельно разбирать разрешённые path-опции и проверять их канонический путь с учётом cwd и symlink. Отклонять абсолютные значения в файловом API. Явно описать доверие к тестовому коду. Для исходников/тестов, которые нельзя менять через Bash, проверять изменения и определить поведение при нарушении, а не полагаться на имя executable.

**Регрессия:** внешние symlink, абсолютные/родительские пути, значения после `=`, относительные пути при вложенном cwd, разрешённые формы unittest и pytest.

**13. P1 — Инструмент с именем bash не исполняет команду через Bash.**

Место: [agent/tools.py](agent/tools.py), строки 236–253; требование — блок 1 HW.md.

Это установленный чтением кода факт: `shlex.split()` и `Popen(parts, shell=False)` запускают программу напрямую. Наличие инструмента с таким именем не выполняет буквальное требование «запускает переданную команду через Bash». Для простого unittest разницы в результате нет, но соответствие спецификации — отдельный вопрос.

**Исправить:** после строгой валидации выполнять команду через явно выбранный Bash. При преобразовании argv обратно в команду корректно экранировать каждый аргумент; не открывать доступ к произвольному shell-синтаксису. Проверять доступность Bash и описать требование к окружению. Простая замена на `shell=True` с непроверенной строкой — плохое исправление.

**Регрессия:** тест запуска подтверждает использование Bash, корректную передачу cwd/аргументов, stdout/stderr/кода выхода; запрещённый синтаксис отклоняется до старта процесса.

**14. P1 — Успех инструмента подменяет проверенный результат задачи; без UI происходит автопринятие.**

Места: [agent/runtime.py](agent/runtime.py), строки 60–95, 308–312, 341–363; [agent/storage.py](agent/storage.py), строки 230–258; [agent/__main__.py](agent/__main__.py), строки 58–70.

Любой возврат executor без исключения становится `succeeded`. У Bash это включает `exit_code=1` и `timed_out=True`. Такой вызов становится кандидатом на завершение задачи. Более того, при `review=None` runtime сам подставляет `(True, '')` и записывает решение будто от пользователя. CLI действительно передаёт callback и спрашивает человека, поэтому проблема автопринятия относится к core API и существующим тестам, а не ко всем интерактивным запускам.

**Подтверждено:** план с задачей «tests pass», запуск заведомо падающего unittest, runtime без review. В БД: `exit_code=1`, call succeeded, task done. Реального подтверждения пользователя не было.

Даже при наличии UI чтение файла может стать поводом закрыть задачу «исправить и проверить»: запрос review появляется сразу после пачки, а не после явного заявления о достижении проверяемого результата. В UI показываются ID, вызов и укороченный result, но не описание задачи и её критерий. `evidence_json` не заполняется; ссылка `completed_call_id` есть и позволяет найти результат, однако сама по себе не делает его достаточным доказательством.

**Исправить:** отделить техническое исполнение от результата проверки. Для проверки тестами принимать только подходящий успешный exit code без timeout; хранить критерий и доказательства задачи. Без review-callback переходить в устойчивое waiting_review, а не выдумывать принятие. Показывать пользователю описание, критерий и существенные результаты; обрезанное сообщение об ошибке не должно выдавать задачу за выполненную.

**Регрессия:** падающие тесты, timeout, успешное чтение вместо исправления, работа без callback, отказ и повторная сдача результата, restart в ожидании review. Done-задачи после reopen не исполняются заново.

**15. P1 — План почти не валидируется, циклы зависимостей принимаются.**

Места: [agent/runtime.py](agent/runtime.py), строки 144–153, 194–214, 374–382; [agent/storage.py](agent/storage.py), строки 213–221.

Проверяются непустой список steps, уникальные строковые ID и существование указанных зависимостей. Не проверяются обязательные поля goal/tools/risks/assumptions/ready_when, описание шага, тип depends_on и отсутствие циклов. Неверный свободный текст автоматически превращается в искусственный «план» с общей целью и критерием `Tests pass`, вместо возвращения модели ошибки структуры.

**Подтверждено:** `{'steps': [{'id': 'one'}]}` проходит `_validate_plan()`. План с зависимостью `one -> one` также проходит. Первый упадёт в approve при обращении к отсутствующему description; второй не даст запустить ни одной задачи. Необъектный элемент steps может вызвать AttributeError вместо контролируемого сообщения для модели.

Ещё одна неполнота: задачи выбираются `ORDER BY task_id`, а исходная позиция шага не хранится. При независимых шагах порядок плана не сохранится; ID вида `step_10` сортируется раньше `step_2`. Это не ломает явно заданные зависимости, но нарушает ожидаемый порядок действий.

**Исправить:** полноценная схема плана, проверка известных инструментов и DAG, сохранение позиции шага. Некорректный план возвращать модели с понятной ошибкой, не утверждать заглушку. Все проверки проводить до записи решения об утверждении.

**Регрессия:** отсутствующие обязательные поля, неверные типы, неизвестные инструменты, пустой ID, цикл/самозависимость, зависимость на неизвестный шаг, минимум три корректные задачи и порядок их запуска.

**16. P1 — При конфликте «удалённый файл заменили каталогом» rollback уже успевает изменить другие файлы.**

Места: [agent/tools.py](agent/tools.py), строки 33–54; [agent/runtime.py](agent/runtime.py), строки 464–489.

Дерево не хранит каталоги. Если агент удалил файл, его final hash равен NULL. Если пользователь создал на этом месте каталог, проверка снова видит отсутствие файла и считает хеш совпавшим. Ошибка обнаруживается только при `unlink()` в фазе восстановления, когда предыдущие пути могли быть уже записаны.

**Подтверждено:** агент меняет `a.txt` и удаляет `b.txt`; пользователь создаёт каталог `b.txt`; rollback восстанавливает `a.txt`, затем падает с `PermissionError` на каталоге. Это внешнее изменение пути, которое следовало обнаружить до любой записи. Нарушено прямое правило ТЗ «при конфликте не перезаписывать ни один файл».

**Исправить:** во время предварительной проверки сверять не только хеш содержимого, но существование и тип каждой записи, в том числе ожидаемое полное отсутствие пути. Не разрешать существующему каталогу совпасть с удалённым файлом. Подготовку данных и проверку возможности восстановления сделать до первой записи; аварийное восстановление самого rollback определить отдельно.

**Регрессия:** конфликт типа на последнем из нескольких путей оставляет все остальные файлы побайтно неизменными. Дополнительно проверить замену родительского каталога ссылкой.

**17. P1 — Исключения журнала слишком широки и не документированы.**

Место: [agent/tools.py](agent/tools.py), строки 41–47; описание журнала — [README.md](README.md), строки 75–79.

Любые `*.db`, `*.sqlite3`, `*-wal`, `*-shm` и содержимое любой вложенной `.agent` исключены из снимков. Инструменты при этом могут их менять. Так за пределами журнала оказывается не только служебная БД агента, но и пользовательские данные проекта. Исключения не перечислены в README, хотя HW.md прямо требует явного описания исключений для генерируемых файлов.

**Подтверждено:** `data.db` с текстом old меняется на new через write_file; в журнале ноль строк; rollback оставляет new. По документации пользователь ожидает обратное.

**Исправить:** исключать конкретные служебные пути, а не все расширения пользовательских данных. Для каждого исключения определить, разрешена ли запись инструментом. Документировать генерируемые файлы; нельзя маскировать такими исключениями исходники и тесты. Если файл не поддерживается журналом, отказать до изменения или явно поддержать его формат снимка.

**Регрессия:** пользовательские `.db`/`.sqlite3`, исходники во вложенных каталогах, служебная БД вне workspace, точный список исключений.

**18. P2 — /diff показывает только последний переход, а не изменения run_id.**

Место: [agent/tools.py](agent/tools.py), строки 314–346.

`original` сохраняется от первого изменения, но `diff` каждый раз вычисляется из локальных `before/after` и перезаписывается. Поэтому в одной строке журнала original/final описывают запуск целиком, а diff — только последний вызов.

**Подтверждено:** old → middle → final. В БД original=old, final=final, но `/diff` содержит `-middle/+final`, без old. При A → B → A журнал может показывать изменение, хотя суммарно файл вернулся в исходное состояние.

**Исправить:** вычислять сводный diff от сохранённого original до текущего final. Историю отдельных действий, если она нужна, хранить отдельно. Нулевое суммарное изменение отображать корректно.

**Регрессия:** несколько правок одного файла, create→modify, modify→delete, create→delete и возврат к исходному содержимому.

**19. P2 — Rollback оставляет SQLite в состоянии до отката.**

Место: [agent/runtime.py](agent/runtime.py), строки 464–489.

Откат меняет только файловую систему. Снимок, final hashes, журнал и статус run не обновляются; решение об откате не сохраняется. Runtime считает собственное восстановление посторонним вмешательством.

**Подтверждено:** выполнить изменение, rollback, затем `continue_prompt()` с новой записью. Инструмент получает `workspace conflict detected before side effect`. Повторный rollback для изменённого файла также сравнивает восстановленный оригинал с устаревшим final hash и конфликтует.

**Исправить:** выбрать ясную семантику: либо откат завершает run терминальным состоянием, либо разрешённое продолжение использует новый сохранённый baseline. Исторические изменения и факт отката сохранять отдельно, не стирать аудит. Повторная команда должна иметь предсказуемый результат.

**Регрессия:** rollback → reopen → status/diff → повторный rollback; продолжение либо явно запрещено, либо работает без ложного конфликта.

**20. P1 — Обязательные приёмочные сценарии почти не покрыты тестами.**

Места: [tests/test_runtime.py](tests/test_runtime.py), [tests/test_client.py](tests/test_client.py).

Текущие 21 тест полезны для отдельных веток, но недостаточны для заявленного уровня проекта. Особенно опасен `test_fault_point_creates_unknown_and_retry_executes` на строках 203–234: сначала он полностью исполняет `_execute_call()` вместе с сохранением результата и журнала, потом SQL-запросом превращает все попытки вызова обратно в started. Это проверка искусственно переделанной БД, а не реального окна между побочным эффектом и сохранением результата. Она скрывает ошибку с лишней попыткой и не проверяет отсутствие журнала после сбоя.

В штатном наборе отсутствуют:

- Полная контрольная задача с `order.py`, реальным запуском `bash` и проверкой неизменности `test_order.py`.
- Положительный multi-call и повтор успешного ID с доказательством отсутствия повторного эффекта.
- Исчерпание каждого из четырёх бюджетов, корректная граница result, сохранение счётчиков после reopen и явного retry.
- Настоящие fault points до эффекта, после эффекта, между записью журнала/result/message, в approve и review.
- Не менее трёх задач с зависимостью, запрет преждевременного запуска и отсутствие повторов done после reopen.
- Восстановление заказа после создания нового Store/runtime и конфликт, при котором не меняется ни один другой файл.
- Fail/abort, несколько unknown, отказ в небезопасном retry, присвоение изменений unknown пользователем.
- Проверки Bash: timeout, bounded output, exit code, cwd, запрещённые аргументы и symlink.
- CLI-сценарии `/resume`, `/resolve`, `/approve`, `/tasks`, `/diff`, `/rollback`.

Большинство recovery-проверок использует тот же Store и тот же runtime, а не закрытие соединения и загрузку состояния заново. Есть прямые обращения к приватному `_execute_call()`, обходящие публичный путь резервирования; такие тесты не доказывают инварианты полного loop.

**Исправить:** превратить критерии HW.md в приёмочную матрицу. Проверять наблюдаемые эффекты, данные БД и входящие сообщения модели одновременно. Подставная модель должна проверять корректность истории и фазы, а не только отдавать следующий ответ из списка. Не менять контрольные тесты, чтобы получить зелёный результат.

**21. P2 — Ошибки модели и команды CLI не всегда обрабатываются как восстановимые ошибки.**

Места: [agent/client.py](agent/client.py), строки 89–105; [agent/__main__.py](agent/__main__.py), строки 144–215, 245, 253–266, 275–282. Выводы этого пункта получены чтением кода; реальные ответы провайдеров не тестировались.

Некорректный JSON аргументов или arguments не-объект превращаются в ModelError всего ответа. Модель не получает ошибку конкретного инструмента и возможность исправиться в том же loop. Если `message` имеет неожиданный тип, `.get()` может дать AttributeError, не переведённый в ModelError. Имена/ID принудительно приводятся к строкам, поэтому часть некорректных значений маскируется вместо валидации.

Обработка `/approve`, `/reject`, `/resolve` вызывается вне внутреннего try для запросов пользователя. Например, `/approve` без плана вызывает RuntimeError, который доходит до верхнего `main()` и завершает CLI. Это нормальная пользовательская ошибка, а не причина закрывать приложение. SQLite-ошибки и часть ошибок схемы также могут выйти traceback.

**Исправить:** валидировать структуру ответа явно; отделить транспортную ошибку от ошибки конкретных аргументов, насколько позволяет сохранённый call ID. Командный диспетчер должен возвращать понятную ошибку и оставлять сессию открытой. Не превращать неожиданные programming errors в мнимый успех.

**Регрессия:** неверный JSON arguments, пустой/некорректный ID, неверный тип message, `/approve` до старта, `/resolve` неизвестного вызова, закрытая/повреждённая БД с понятной диагностикой.

**22. P2 — Обещание «любой OpenAI-compatible provider» не подтверждается адаптером.**

Места: [README.md](README.md), строка 20; [agent/client.py](agent/client.py), строки 79–87.

Для всех адресов, кроме двух строковых вариантов локального Ollama, запрос безусловно получает `reasoning_effort`. Это эвристика по URL, а не настройка возможностей API: другой хост Ollama тоже попадёт в эту ветку. Из кода нельзя вывести, что каждый заявленный провайдер поддерживает это дополнительное поле. В тестах проверяется обычный текстовый ответ, но не полноценный обмен tool_calls с реальным совместимым сервером.

Это риск совместимости, а не подтверждённый в обзоре сетевой отказ: внешние API не вызывались.

**Исправить:** необязательные расширения протокола включать явно по конфигурации, по умолчанию отправлять минимально необходимый запрос. Проверить tool calling на выбранном для защиты сервисе. В README назвать действительно проверенный вариант настройки и ограничения вместо универсального обещания.

**23. P2 — Core смешивает правила, SQL и текст интерфейса, что усложняет исправление состояния.**

Места: [agent/runtime.py](agent/runtime.py), строки 44–58, 155–160, 335–370, 415–421, 464–489; [agent/__main__.py](agent/__main__.py), строки 126–141, 186–198; [agent/storage.py](agent/storage.py).

AGENTS.md требует структурированных результатов core и форматирования в CLI. Сейчас runtime форматирует человеческие сообщения о бюджете, статусе и результатах; некоторые управляющие результаты возвращаются обычной строкой. При этом и runtime, и CLI напрямую используют `store.db`. Поэтому переход состояния оказывается размазан между несколькими слоями и отдельными коммитами. `_safe_loop()` содержит запрещённый правилами проекта широкий `except Exception` и сводит бюджет, конфликт и ошибку к общему failed.

В схеме нет CHECK-ограничений допустимых статусов, систематических внешних ключей и включения `PRAGMA foreign_keys=ON`. Повторные INSERT OR REPLACE способны скрывать ошибочные переходы. Константы лимитов дублируются в runtime/config, потенциально меняющие инструменты перечисляются вручную в нескольких местах. Это не отдельный повод переписывать проект с нуля, но текущая организация помогает ошибкам № 1–10 оставаться незаметными.

**Исправить:** небольшие операции Store для законченных переходов; типизированные статусы, ошибки и события; форматирование событий в CLI. Метаданные инструмента должны включать effect/retry policy, чтобы новый executor не забыли учесть в бюджете и Plan Mode. Возвращать структурированные состояния ожидания, завершения и конфликта. Обрабатывать ожидаемые доменные ошибки узко.

**В каком порядке чинить.**

1. Исправить одну попытку на одно исполнение, настоящие транзакции Store и восстановление недостающих сообщений. Это основание остальных уровней.
2. Закрыть обходы Plan Mode и полный автомат состояний unknown/fail/abort; восстанавливать план и атомарно создавать задачи.
3. Привязать run к сохранённому workspace, сохранять точные исходные данные и реализовать согласование неизвестных изменений. До этого не считать rollback безопасным.
4. Проверять result-бюджет до эффекта; исправить таймаут, учёт/усечение вывода и проверки аргументов Bash; выполнить буквальное требование запуска через Bash.
5. Валидировать план/DAG и сделать проверяемое завершение задач без автопринятия. Добавить обязательные три зависимые задачи и reopen-тесты.
6. Исправить aggregate diff, состояние после rollback и исключения журнала; синхронизировать README с реальными гарантиями.

Не стоит начинать с расширения списка команд, нового UI или дополнительного провайдера: они не исправят нарушенные инварианты, по которым оценивается эта работа.

**Минимальное воспроизведение двух основных ошибок.**

Запустить из корня проекта. Скрипт работает только во временных каталогах; код и контрольный workspace не меняет. Первая часть показывает лишнюю started-попытку, вторая — изменение файла при result=0.

```python
import tempfile
from pathlib import Path

from agent.client import AssistantTurn, ToolCall
from agent.runtime import AgentRuntime
from agent.storage import Store


class FakeModel:
    def __init__(self):
        self.turns = iter([
            AssistantTurn("", [ToolCall("c", "write_file", {
                "path": "a.txt", "content": "new"
            })]),
            AssistantTurn("done", []),
        ])

    def complete(self, messages, tools):
        return next(self.turns)


for result_limit in (1000, 0):
    with tempfile.TemporaryDirectory() as directory:
        base = Path(directory)
        workspace = base / "workspace"
        workspace.mkdir()
        (workspace / "a.txt").write_text("old", encoding="utf-8")
        store = Store(str(base / "state.sqlite3"))
        try:
            runtime = AgentRuntime(
                FakeModel(), store, str(workspace),
                limits={"model": 3, "tools": 3,
                        "effects": 3, "result": result_limit},
            )
            try:
                runtime.start("change a.txt")
            except RuntimeError as exc:
                print("error:", exc)
            print("result limit:", result_limit)
            print("file:", (workspace / "a.txt").read_text(encoding="utf-8"))
            print("attempts:", [tuple(row) for row in store.db.execute(
                "SELECT attempt, status FROM calls ORDER BY attempt"
            )])
        finally:
            store.close()
```
