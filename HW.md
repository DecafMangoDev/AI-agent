# Домашнее задание № 1. Coding agent с tool calling

**Дедлайн: 30 октября 2026 года.**

## Задача

Соберите консольного агента, который получает задачу на изменение небольшого проекта, сам выбирает инструменты, читает и меняет файлы, запускает тесты и решает, когда закончить работу.

Сложность здесь не в объёме кода. Вам нужно спроектировать runtime агента: отделить решение модели от исполнения инструментов, сохранить состояние после сбоя и контролировать расход ресурсов.

Агента можно писать на любом языке программирования. Python ниже используется только для общего проверочного проекта, а не как требование к реализации агента.

## Тестовая задача

Агент должен справиться с таким запросом:

> Исправь расчёт итоговой стоимости заказа, чтобы тесты проходили. Тесты не меняй. Сам найди нужные файлы, внеси исправление и запусти тесты.

`workspace/order.py`:

```python
def calculate_total(prices: list[float], discount_percent: float) -> float:
    return sum(prices) - discount_percent
```

`workspace/test_order.py`:

```python
import unittest

from order import calculate_total


class OrderTest(unittest.TestCase):
    def test_discount(self) -> None:
        self.assertEqual(calculate_total([100, 50], 10), 135)

    def test_invalid_discount(self) -> None:
        for value in (-1, 101):
            with self.assertRaises(ValueError):
                calculate_total([100], value)
```

Сложность исправления `order.py` на оценку не влияет.

## Базовая часть, до 7 баллов

### Блок 1. Agent loop и инструменты, 3 балла

Реализуйте агентский цикл с tool calling. Модель должна сама решать, какой инструмент вызвать, нужен ли следующий шаг и когда можно вернуть финальный ответ.

Обязательный инструмент - `Bash`: он принимает команду и рабочую директорию, запускает переданную команду через Bash и возвращает `stdout`, `stderr` и код завершения. Кроме него нужен хотя бы один инструмент чтения файлов и один инструмент изменения файлов; конкретный набор выберите сами. Вместе инструменты должны позволять агенту найти и прочитать файлы, изменить код и запустить тесты. Например:

```text
Bash(command, cwd)  # обязательно
list_files(path)
read_file(path)
write_file(path, content)
apply_patch(patch)
```

Каждый инструмент передаётся модели с именем, описанием и JSON Schema аргументов. Runtime проверяет имя и аргументы до выполнения. Результат инструмента возвращается модели сообщением `role: tool` с исходным `tool_call_id`.

Цикл должен поддерживать несколько tool calls в одном ответе модели, ошибки инструментов и нормальное завершение текстовым ответом. Ошибка инструмента не должна ронять весь процесс: модель получает понятный результат и может выбрать другой шаг.

Для контрольной задачи используйте учебную копию проекта в `workspace` без секретов. `Bash` запускается с ограничением времени и размера вывода. Через него нужно уметь запустить тесты, например:

```bash
python3 -m unittest -v
```

Способ организации модулей, дополнительные инструменты, формат успешных результатов и интерфейс запуска выберите сами. В тесте покажите, что агент действительно использует `Bash` для проверки исправления, а `test_order.py` остаётся неизменным. На Windows используйте WSL или другую среду с Bash; имя команды Python в ней может отличаться.

### Блок 2. Восстановление после сбоя, 3 балла

Каждый запуск получает `run_id`. Сохраняйте достаточно данных, чтобы после перезапуска продолжить работу: историю сообщений, tool calls, их результаты, решения пользователя и текущее состояние. Если реализован уровень на 8 баллов, сохраняйте и потраченный бюджет.

Уже завершённое действие после восстановления не выполняется повторно. Перед действием с побочным эффектом, включая `Bash`, runtime сохраняет, что оно началось, а после выполнения сохраняет результат. Если между этими записями процесс упал, вызов считается неопределённым и не запускается молча ещё раз. Пользователь выбирает одно из действий:

1. повторить, если инструмент безопасно повторяем;
2. считать шаг неуспешным и продолжить;
3. завершить запуск с ошибкой.

Обычный повтор `tool_call_id` не должен приводить к повторному изменению файлов. Если имя инструмента или аргументы отличаются от сохранённых, runtime возвращает ошибку протокола. Явный повтор неопределённого вызова оформляется как новая попытка того же tool call. Какие инструменты можно безопасно повторять, решите и обоснуйте сами.

Формат хранилища, набор статусов и способ имитации сбоя выберите сами. В тестах должна быть управляемая точка отказа между выполнением инструмента и сохранением результата.

### Блок 3. Plan Mode, 1 балл

Добавьте отдельный режим планирования. До подтверждения плана агент может изучать проект инструментами чтения, но не может менять файлы, удалять их или вызывать `Bash`.

Результат Plan Mode хранится как структурированные данные и содержит:

1. цель работы;
2. шаги в предполагаемом порядке;
3. инструменты, которые понадобятся на каждом шаге;
4. риски, допущения и критерий готовности.

План сохраняется вместе с `run_id`. Агент ждёт явного решения пользователя: утвердить план или отклонить его. Исполнение начинается только после утверждения.

Тест должен доказывать, что до утверждения плана не произошло ни одной операции с побочным эффектом.

## Уровень на 8 баллов. Бюджеты агента

Добавьте единый бюджет запуска с лимитами хотя бы на:

1. число запросов к модели;
2. число tool calls;
3. число действий с побочным эффектом;
4. суммарный размер результатов инструментов.

Бюджет действует на все фазы одного `run_id`: планирование, исполнение и восстановление. `resume`, утверждение плана и повтор после сбоя не обнуляют счётчики.

Проверка лимита и списание должны сохраняться атомарно вместе с состоянием действия. Если процесс упал после списания, потраченный бюджет не возвращается. Действие не должно начаться, если нужный лимит уже исчерпан.

Учтите два пограничных случая:

1. если модель вернула несколько tool calls, а остатка не хватает на всю пачку, ни один вызов из неё не выполняется;
2. если размер результата заранее неизвестен, инструмент получает доступный остаток, а runtime обрезает вывод и явно помечает его как неполный.

Значения лимитов и формат настройки выберите сами. В тестах покажите исчерпание каждого лимита, сохранение счётчиков после `resume` и сбой между списанием бюджета и сохранением результата.

## Уровень на 9 баллов. Разбиение плана на задачи

Превратите шаги плана в задачи, которыми runtime умеет управлять. У каждой задачи есть идентификатор, описание, зависимости, состояние и проверяемый результат.

Runtime запускает задачу только после успешного завершения её зависимостей. Последовательного исполнения достаточно, параллельность не требуется. На фазе исполнения каждый tool call связан с текущей задачей. Вызовы во время планирования хранятся отдельно и не требуют `task_id`.

Состояние задач и фактические результаты сохраняются вместе с запуском. Одного текстового заявления модели недостаточно, чтобы пометить задачу завершённой: runtime должен зафиксировать подтверждение её результата. Вид этого подтверждения выберите сами. В детерминированном тесте используйте минимум три задачи, среди которых есть хотя бы одна зависимость. После `resume` завершённые задачи не запускаются заново. Задачи должны писаться в stdout в формате чеклиста

## Уровень на 10 баллов. Журнал изменений и откат

Добавьте возможность посмотреть изменения конкретного `run_id` и откатить их по явной команде пользователя. Журнал должен охватывать создание, изменение и удаление файлов проекта. Для каждого затронутого файла сохраняйте исходное состояние до первого изменения, итоговое состояние после последнего изменения и хеши, по которым можно обнаружить постороннюю правку.

Перед каждым действием, которое может менять файлы проекта, сверяйте текущее дерево с последним сохранённым состоянием и сохраняйте новый снимок. Снимок включает содержимое файлов и список путей, чтобы фиксировать также создание и удаление файлов. Если состояние уже отличается, остановите действие и сообщите о конфликте. После действия сохраните фактический diff и хеши. Это относится и к `Bash`, если запущенная команда может менять файлы проекта. Можно ограничить `Bash` командами, которые не меняют исходники и тесты. Исключения для генерируемых файлов укажите явно; они не должны скрывать исходники или тесты контрольного проекта.

Откат восстанавливает только файлы, изменённые этим запуском, и не трогает остальные. Перед откатом runtime сверяет текущие хеши с журналом изменений. Если после последнего действия агента хотя бы один из этих файлов изменился извне, runtime сообщает конфликт и не перезаписывает ни один файл. Журнал и команда отката работают после `resume`. Неопределённый после сбоя вызов сначала разрешается по правилам блока 2: runtime сверяет дерево и показывает обнаруженные изменения пользователю, а пользователь явно решает, относить ли их к этому запуску. До этого откат не выполняется.

В детерминированных тестах покажите изменение `order.py`, просмотр diff, восстановление исходного файла после перезапуска и конфликт при постороннем изменении файла.

## Бесплатный доступ к модели

Можно использовать учебный или корпоративный доступ либо любой доступный из вашей сети сервис с бесплатным лимитом и OpenAI-compatible Chat Completions API. Покупать API-ключ для домашней работы не нужно.

Локальная Ollama нужна только как запасной вариант, если другие модели недоступны. В одном терминале загрузите модель и запустите сервер:

```bash
ollama pull qwen3:4b
ollama serve
```

Во втором терминале задайте переменные окружения, установите зависимости и запустите своего агента командой из `README.md`:

```bash
export OPENAI_BASE_URL=http://localhost:11434/v1/
export OPENAI_API_KEY=ollama
export OPENAI_MODEL=qwen3:4b
```

Для PowerShell:

```powershell
$env:OPENAI_BASE_URL = "http://localhost:11434/v1/"
$env:OPENAI_API_KEY = "ollama"
$env:OPENAI_MODEL = "qwen3:4b"
```

Ollama не проверяет значение ключа, но некоторым SDK нужна непустая строка. Справка: [совместимость с OpenAI API](https://docs.ollama.com/api/openai-compatibility), [tool calling](https://docs.ollama.com/capabilities/tool-calling), [модели Qwen 3](https://ollama.com/library/qwen3).
